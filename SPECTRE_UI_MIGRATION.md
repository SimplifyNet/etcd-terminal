### Незавершённый вертикальный срез

По прочитанным исходникам контракты и потребители несовместимы:

- `App/Screens/Keys/KeyBrowseLayout.cs`: в `PanelModel` передаются строки вместо `PanelLine`.
- `Infrastructure/Terminal/SpectrePanelRenderer.cs`: `Markup.Escape` вызывается для `PanelLine`, а не строки.
- `App/Components/StatusBar.cs` и `Infrastructure/Terminal/SpectreStatusBarRenderer.cs`: используются отсутствующие в новой модели `LeftHints`, `Name`, `Connection`, `Username`.
- `PanelMigrationTests`, `LayoutTests`, `SessionFlowTests` ещё содержат ожидания старой структуры моделей.

Это статически видимые несоответствия, не отчёт выполненной сборки. Нельзя считать незавершённый worktree рабочим эталоном UI.

### Почему пропали цвета

`KeyBrowseLayout` собирает подписи и значения в обычные строки. Различие между цветом клавиши, подписи, числа и выбранного ключа теряется до рендера. Оба новых renderer не преобразуют `TextRole` в Spectre `Style`.

`SpectreStatusBarRenderer` использует `NoBorder().BorderColor(PanelBackground)`. Цвет невидимой рамки не задаёт фон содержимого. Аналогично фон текста не гарантирует фон padding и пустой области панели.

### Почему футер дублируется и появляется внутри контента

`SpectreStatusBarRenderer.Write` вызывает обычный `AnsiConsole.Write(Build(model))`: это дописывание в текущую позицию, а не обновление закреплённого региона.

При этом независимые вызовы статус-бара остались в `ScreenLayout`, `Menu`, `KeyBrowseControl`, `Prompt`, `PressAnyKeyPrompt`, `MultiLinePasteReader`. Например, `ScreenLayout.RenderHeader` сначала выводит футер и возвращает курсор назад, а `KeyBrowseControl.Render` затем выводит футер снова. `Menu` после записи последнего пункта без завершающего перевода строки вызывает статус-бар в текущей позиции.

`StatusBar.RenderPreservingCursor()` теперь просто вызывает `Render()`, то есть название больше не соответствует поведению. `ReservedRows` и `EnsureCursorAboveBar` сохраняют старую геометрию, не согласованную с новым renderer.

Причина системная: потоковый API вывода подставлен вместо обновления фиксированной области, но прежние владельцы вывода и перемещения курсора сохранены. Точный визуальный результат на разных размерах терминала пока не воспроизведён.

## Целевая структура

```text
Domain / Application
  бизнес-данные, правила, use cases
              ^
              | использует
App: Screens / Components / Engine
  локализация, доступность действий, UI-состояние, навигация
              |
              v
Presentation contracts
  данные, семантические роли, интерфейсы операций и результатов ввода
              ^
              | реализует
Infrastructure: Spectre rendering / interactive adapters
  маппинг, композиция renderables, один владелец консоли
```

Связывание реализаций выполняется только в `App/Setup/IocRegistrations.cs`.

### Presentation

Меню принимает пункты со стабильными ID, текстом и доступностью. Компонент определяет доступные действия, формирует модель, запрашивает выбор через контракт и обрабатывает результат. Его ответственность не включает вычисление ширины label, циклы заливки, координаты строк или реализацию библиотечного редактора ввода.

Описание формы означает логическую структуру: заголовок, список, действия, футер, выбранный элемент, семантическое оформление. Физические размеры регионов и `Padding` Spectre настраиваются только в Infrastructure. Не передавать `WindowWidth`, `CursorTop`, ANSI, Spectre markup или строки, дополненные пробелами до ширины экрана, через UI-модели.

Сбор данных сессии и локализация остаются в `StatusBar`. Фильтрация, права E/D, выбранный ключ и переходы остаются в `KeyBrowseScreen`/`KeyBrowseControl`. Presentation имеет право использовать бизнес-сервисы; это не делает его Domain.

### Infrastructure

Организовать один модуль маппинга в существующей области `Infrastructure/Terminal` либо в её тематическом подкаталоге. Переиспользовать `SpectrePanelRenderer` и `SpectreStatusBarRenderer`, не заводить альтернативную систему панелей.

- Один общий преобразователь `TextRole` + `ITheme` в `Style`; конкретное имя выбрать при реализации.
- `StyledText` отображать буквальным `Text`/`Paragraph.Append(text, style)`; `PanelLine` преобразовывать в строковый renderable, коллекции строк собирать библиотечными средствами.
- Панели, таблицы, выравнивание, padding, переносы и обрезание делегировать Spectre.
- Построение дочернего renderable отделить от физического вывода. В составе экрана дочерние renderer ничего самостоятельно не дописывают в консоль.
- Один screen host владеет кадром и интерактивной сессией. Это реализация Presentation-контракта, а не сервис, доступный только через Infrastructure-тип.

`ITheme` и `RgbColor` могут описывать палитру, но это UI-контракты. Компоненты выбирают роли, а не вычисляют escape-коды.

### Физическое разделение сборок

Для окончательного отделения от Domain выделить dependency-free проект `src/EtcdTerminal.Presentation/EtcdTerminal.Presentation.csproj` с моделями и UI-контрактами. Это планируемый проект, сейчас его нет.

Перенести туда `Presentation`, контракты темы/локализации и остающиеся нужными UI/input-контракты. `TableData`, `MenuItem`, `ITextInput` сначала проверить на пригодность, не заменять ради переименования. Удаляемые legacy-интерфейсы не переносить автоматически. Технические environment/lifecycle-порты классифицировать по реальным потребителям; не выдавать их за бизнес-контракты.

`App` и `Infrastructure` ссылаются на Presentation и нужные business/application assemblies; Domain на Presentation не ссылается. Добавить проект в `src/EtcdTerminal.slnx`, исправить references, DI и архитектурные проверки. Существующие namespaces можно сохранить, если это уменьшает diff и не скрывает смысл границ. Отдельный Application-проект не создавать только ради симметрии: выделять реальные use cases по мере необходимости.

## Решения До Реализации Host

### Футер и ввод

Кандидат: одна композиция `Layout` внутри управляемой `Live`-сессии, при необходимости в библиотечном alternate screen. Разделы header/body/actions/footer обновляются в одном кадре. Это нужно подтвердить в PTY, а не объявить готовым свойством Spectre.

Нельзя просто обернуть существующий `Prompt` в этот Live. Штатные prompts не предоставляют готового API ввода внутри заданного body с постоянно закреплённым футером. Остановка Live перед prompt также сама по себе не сохраняет закрепление футера.

До основного переписывания проверить минимальный прототип: обычный кадр, повторные обновления, ввод с валидацией и Escape, возврат в кадр, resize. Если одновременно выполнить паритет и запрет ручного rendering не получается, предъявить пользователю конкретное ограничение и варианты. Возможные компромиссы: отдельно согласованное поведение футера во время штатного prompt либо минимальный input-адаптер с библиотечной отрисовкой. Ни один компромисс этим документом не одобрен. Не переписывать `TextPrompt`/`SelectionPrompt` в собственный UI-framework без необходимости и согласования.

### Фон

Проверить фон текста, внутреннего padding и свободной области панели раздельно. Сначала исследовать доступные библиотечные способы стиля в `0.57.2`. Если для сплошного фона понадобится собственная обработка render segments, описать узкую задачу адаптера и получить согласование. Не возвращать заполнение строк пробелами и ANSI под видом исправления цветов. Исчезновение заливки тоже не является приемлемым молчаливым решением.

### Переполнение

Логическая страница ключей сейчас по умолчанию содержит 30 элементов, настройка допускает до 500. `Layout` не превращает их автоматически в прокручиваемый интерактивный список.

Определить политику видимости выбранного элемента, длинного меню, длинных значений, уменьшения окна и слишком маленького терминала. Не подменять бизнес-пагинацию расчётом строк терминала в Presentation. Физическую политику ограничений реализует Infrastructure средствами Spectre; доступность действий и данных не должна теряться. Для redirected/noninteractive output определить отдельное поведение, не выдавая потоковый вывод за интерактивный паритет.

## Порядок Разработки

### 1. Завершить Semantic Spans

Первый небольшой вертикальный срез, без обещания исправить закрепление футера:

1. Согласовать `KeyBrowseLayout`, `StatusBar`, оба Spectre renderer и тесты с уже существующими моделями.
2. Добавить общее преобразование ролей в `Style`; исключить дублирование палитры по renderer.
3. Сохранить отдельные spans для подписей, значений и разделителей. Выбранный ключ: `Accent`; клавиши E/D/Esc: `Primary`, подписи: `Muted`; числа пагинации: `Primary`, подписи: `Muted`; имя подключения: `Secondary`, пользователь: `Warning`, разделители: `Subtle`, индикатор подключения: `Success`, значение версии: `Primary`. Сверить с прежней темой и поведением.
4. Определить `Default` и единственного владельца форматирования версии. Не собирать одну версию одновременно из `Version` и `Right` в двух местах; не добавлять fallback старых свойств без внешней необходимости.
5. Сохранить буквальность заголовков, ключей, IPv6 и brackets. Отделить нормализацию control characters в `ValuePreview` от обрезания по display width; sanitization не удалять.
6. Обновить DI при появлении общего mapper, запустить build и unit tests. Проверить цвета на настоящем терминале; незавершённые фон и placement отметить явно.

Результат: согласованные контракты и семантика foreground. Это промежуточный результат, не приёмка всей миграции.

### 2. Доказать Композицию И Lifecycle

1. Выполнить прототип и закрыть решения из предыдущего раздела до массового изменения callers.
2. Ввести минимальный data-only контракт кадра и интерфейс host только в объёме подтверждённой реализации. Возможные названия `ScreenModel`/`IScreenHost` являются предложением, таких типов сейчас нет.
3. У модели только логические регионы и состояния. Операции запуска, обновления, ввода и завершения принадлежат интерфейсам, не callback-полям модели.
4. `ScreenLayout` собирает логическую композицию; Infrastructure создаёт `Layout` и управляет выводом. `StatusBar` предоставляет модель, но не выбирает строку и не скроллит.
5. У host один экземпляр на консоль и явный begin/update/end lifecycle. В `finally` освобождать интерактивный контекст и восстанавливать состояние через библиотеку, в том числе при cancellation/exception.
6. Зарегистрировать host и общий экземпляр консоли в `IocRegistrations`. `SpectreTextInput`/`EscapableConsole` и renderers должны использовать согласованную консоль, не создавать независимых владельцев. Учесть `Program.cs` initialization, recovery loop и cleanup.

При невозможности обязательного паритета без исключений остановить именно этот этап с описанием blocker. Не подменять приёмку незаметным упрощением дизайна.

### 3. Перевести Целый Экран Ключей

- `KeyBrowseLayout`: формировать модели поиска, списка, выбранного ключа, пагинации и действий. Заменить ручные колонки на `Table`/`Grid` в mapper.
- `KeyBrowseControl`: сохранить команды и состояние, удалить `SearchEndCol`, `SearchBarRow`, cursor reposition и самостоятельный вывод футера.
- `KeyBrowseScreen`: сохранить фильтр после edit/delete, выбранный элемент, права изменения, счётчики и отмену; прямые writes деталей также заменить моделями.
- Обновлять один кадр, а не дописывать несколько панелей. Старый renderer не должен оставаться скрытым fallback для этого экрана.
- Удалить соответствующие width/padding/fill алгоритмы и их тесты после исчезновения потребителей.

### 4. Перевести Остальной Интерактив

| Текущий компонент | Изменение | Что сохранить |
| --- | --- | --- |
| `Engine/Menu`, `Components/MenuScreen` | Штатный `SelectionPrompt`, если подтверждён паритет, либо согласованный адаптер; убрать собственный построчный redraw | ID, одинаковые labels, недоступные пункты/разделители, циклическая навигация, Enter/Escape |
| `Engine/Prompt`, `SpectreTextInput`, `EscapableConsole` | Согласовать с host; переиспользовать `TextPrompt` и существующую обработку Escape | trim, empty/null, editable default, secret, validation/cancellation |
| `Components/Spinner` | Переиспользовать `Status` в допустимом lifecycle, не запускать его внутри Live | completion, cancel и распространение ошибок |
| `MultiLinePasteReader`, `PressAnyKeyPrompt` | Убрать собственные перерисовки футера; согласовать input state | многострочная вставка, queued input, Escape, отсутствие утечки введённого секрета |
| `Header`, `Message` | Модели содержимого и семантики; Figlet и стили в Infrastructure | тексты, роли success/error/warning |
| `UserListRenderer`, `RoleListRenderer`, `PermissionViewRenderer` | Builders таблиц, переиспользовать пригодный `TableData` | локализация, содержимое, разрешения |
| `KeyImportJsonScreen`, `InstanceSelectionScreen`, остальные screens | Убрать оставшиеся прямые rendering writes | preview, empty-state и переходы |

Не удалять смысловую логику ввода только потому, что она не относится к бизнес-домену. Цель удаления: повторная реализация библиотечного рендера, а не вся Presentation-логика.

### 5. Закрепить Границы И Удалить Legacy

Выполнить физическое разделение UI-контрактов, описанное выше, и удалить неиспользуемое:

- строковые ANSI-цвета и методы заливки в `ITerminalStyle`/`ITerminalOutput`;
- cursor-rendering зависимости Presentation, `ReservedRows`, `EnsureCursorAboveBar`, ручной redraw меню;
- `ConsoleTerminal`-алгоритмы width, padding, clear-line, escape generation; готовые Table/Figlet-адаптеры переиспользовать;
- `DisplayCells` и ANSI-aware truncation после отделения нужной sanitization и исчезновения всех production callers;
- геометрические fake terminal и проверки их реализации, когда исчезнет последний осмысленный потребитель.

Прямой `System.Console` при действительно необходимом lifecycle/input допустим только в Infrastructure, но не как средство восстановления ручной отрисовки. Результат должен уменьшать собственный rendering-код, а не просто перемещать его или заменять новой универсальной прослойкой.

## Тесты И Приёмка

### Оставить Небольшой Набор

- Модели: текст и роли, выбранный элемент, E/D только при наличии прав, информация сессии и отсутствие старой сессии после выхода.
- Поведение: `MenuTests`, `PromptTests`, `KeyBrowseScreenTests`, `MultiLinePasteReaderTests`, `SpinnerTests`, `SessionFlowTests`; адаптировать harness к новым контрактам, не привязывать к курсору.
- Мапперы: несколько `TestConsole`-тестов буквального текста и thin-проверок соответствия roles/styles. Проверять собственное преобразование, не алгоритмы измерения/рамок Spectre.
- Архитектура: отсутствие Spectre/Console/ANSI/геометрии в Domain и Presentation; Infrastructure не зависит от App; UI-контракты data-only. Учесть, что reflection-проверка одних сигнатур не видит запрещённые вызовы в телах методов.
- Существующие domain/application/security/integration tests сохранить по назначению.

`LayoutTests` сейчас используют capture-only renderer отдельно от `RecordingTerminal`; их геометрические assertions не видят новые Spectre-панели. Они не доказывают отсутствие overflow или inline footer. Не расширять fake до собственного эмулятора терминала.

`StatusBarPersistenceTests.cs` уже удалён предыдущей попыткой. Его полезное требование, информация активной сессии во время prompt/press-any-key, должно остаться в новых model/host tests и PTY-сценариях. Геометрические assertions старого механизма восстанавливать не нужно.

Количество UI-тестов и объём ручного rendering должны уменьшиться по итогу. Это результат делегирования Spectre, а не квота на удаление поведенческих проверок. В отчёте перечислить удалённые алгоритмы и обслуживавшие их тесты; не добавлять новый набор exhaustive width/Unicode/cursor snapshots.

### Проверка В Терминале Или PTY

| Сценарий | Критерий |
| --- | --- |
| Меню и экран ключей, несколько обновлений подряд | Один футер внизу viewport; панели не дублируются и не появляются на строке выбранного пункта |
| Выбор, поиск, pagination, readonly | Цвета и семантика сохранены; все доступные действия достижимы |
| Prompt, validation error, Escape, возвращение | Футер остаётся внизу; нет конфликтов интерактивных сессий, потерянного ввода или старых панелей |
| Secret, editable default, multiline paste | Поведение сохранено, секрет не попадает в видимый вывод/логи |
| Spinner, cancellation, exception | Операция завершается корректно, консоль пригодна для следующего экрана |
| Подключение и выход из сессии | Актуальные сведения, username только по условиям приложения, версия один раз |
| Узкий/низкий терминал и resize | Работает выбранная политика overflow; выбранный пункт и действия не становятся недоступными |
| Длинные значения, brackets, IPv6, CJK/emoji, control characters | Буквальный безопасный текст; без markup-инъекций и возврата собственного display-width движка |
| Фон панелей и футера | Проверены текст, padding и свободные области, не только цвет рамки |

Записать терминал/PTY, размеры, capability profile, сценарии и фактический результат. Если сценарий не проверен, так и написать. При несовместимости требований нужно явное решение пользователя, а не отметка «готово».

### Команды Для Исполнителя

Из корня репозитория:

```sh
dotnet build src/EtcdTerminal.slnx
dotnet test src/EtcdTerminal.Tests/EtcdTerminal.Tests.csproj
dotnet run --project src/EtcdTerminal.App/EtcdTerminal.App.csproj
```

Последнюю команду выполнять в интерактивном терминале/PTY. Интеграционные тесты запускать при наличии требуемого etcd-окружения; недоступность окружения указать в отчёте.

### Готовность

Миграция принята только при совместном выполнении условий: сборка и релевантные тесты проходят; паритет проверен; нет независимых записей футера; Presentation и Domain не содержат технического rendering; собственные ANSI/width/cursor/fill алгоритмы удалены либо конкретное исключение явно согласовано; UI-тестовая нагрузка уменьшена без потери поведения. Одних моделей, наличия `Panel` или зелёных текстовых snapshots недостаточно.

## Краткая Задача Для Следующего Исполнителя

Прочитай `AGENTS.md` и этот документ, перепроверь текущее дерево и версию Spectre. Начни с завершения semantic spans через существующие модели, producers, общий style mapper и тесты. Затем докажи на небольшом PTY-прототипе жизнеспособность одного владельца кадра с нижним футером и переходами ввода. Не обещай, что `Layout`/`Live` автоматически совместимы с prompts. После подтверждения или явного согласования ограничений мигрируй экраны целиком, отдели UI-контракты от Domain и удали ручные rendering-алгоритмы вместе с их геометрическими тестами. Не считай сломанный worktree эталоном, не ослабляй паритет без разрешения. В конце приложи результаты проверок и список оставшихся ограничений.
